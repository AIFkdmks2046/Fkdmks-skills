# 测试用例审查（角色 · 只审不改）

## Overview

站在"即将照着这些用例去点页面的人"的视角，找出会让执行卡住或漏测的问题，输出**明确结论 + 可执行的修改意见**。

核心原则：**结论先行，问题必须能定位到具体用例 ID**。

## When to Use

- 用例设计完成后、端到端执行之前
- 用例被上一轮审查打回后重写完成，需要再审一次
- 不适用：编写用例（madmax-dev-cases）、执行用例（madmax-dev-e2e）

## 输入与输出

| 项 | 值 |
|---|---|
| 输入 | PRD 路径、`test-cases.md` 路径、（必要时）设计文档路径 |
| 输出 | `.qoder/qa/<slug>/test-review-r<N>.md`（N = 本轮审查轮次，首次为 r1） |

## 审查标准（五条，逐条查）

1. **需求覆盖完整性**：PRD 每个需求点、每条验收标准是否都有对应用例；对照用例文件的"覆盖检查表"核验，并抽查用例正文确认该用例真的验证了它声称的需求点。
2. **步骤可执行性**：是否无歧义、可复现——别人照做能得到同一结果。检查控件是否点名、输入值是否具体、步骤顺序是否明确。
3. **预期结果可判定**：是否写了客观可判定的结果（具体文案/状态/数据），而非"显示正常""功能可用"。
4. **优先级合理性**：P0 是否只用于核心主流程与资损/安全用例；P2 是否塞进了本该 P0/P1 的内容；主流程与异常路径的优先级是否与业务影响匹配。
5. **边界覆盖**：空值、超长、重复提交、并发/刷新/返回、网络异常、权限差异、极值——该有的边界用例是否缺失。

另查**结构合规**：是否含固定字段（ID/模块/优先级/前置条件/操作步骤/预期结果/PRD需求点）、ID 是否连续、覆盖检查表是否覆盖全部需求点。

## 判定规则

输出 `PASS` 的条件（全部满足）：需求覆盖完整 + 无步骤不可执行 + 无不可判定预期 + 优先级无明显错配 + 关键边界无缺失 + 结构合规。

只要存在下列任一情况即 `FAIL`：
- 某个 P0 级需求点或验收标准无任何用例覆盖（无合理豁免说明）
- 存在无法照做的步骤（缺控件名/缺输入值/含歧义）
- 存在不可判定的预期结果
- ID 断号、字段缺失、覆盖检查表缺行

**注**：P2 级用例缺失、边界类建议等不影响 PASS，写进"建议"区即可。

## 输出格式

```markdown
# 测试用例审查报告 r<N>

## 结论
PASS | FAIL

## 阻断问题（必须修，逐条引用用例 ID）
1. [TC-07] 步骤 2 "点击保存" 未指明按钮文案与所在页面，操作人无法定位 → 改为"在订单详情页点击底部『提交订单』按钮"

## 建议（不阻断）
1. [TC-03] 建议补一条 P2 用例覆盖超长标题截断

## 覆盖核验
| PRD需求点 | 结论 | 覆盖用例ID |
|---|---|---|
| R1 | 通过 | TC-01, TC-02 |
| R4 | 不通过 | 无 |
```

每条阻断问题必须**引用用例 ID + 指出具体位置 + 给出可执行的改法**。只写"建议完善"这类无定位意见视为无效输出。

## 角色边界（不可越界）

- **只审不改**：不修改 `test-cases.md`，不替设计者重写用例，只给意见。
- 不执行测试、不碰代码。
- 不擅自改需求判定标准（PRD 是唯一需求依据）。

## 常见错误

| 错误 | 纠正 |
|---|---|
| 输出"整体质量不错，建议完善" | 必须给 PASS/FAIL 结论 |
| 意见不引用用例 ID | 无定位的意见无法执行 |
| 只说"缺少异常用例" | 指明缺的是哪条需求点下的哪种场景 |
| 顺手把用例改了 | 只审不改；改了就没法验证设计者是否学会 |
| 把 P2 建议当阻断项 | 只有影响覆盖/可执行/可判定的才是阻断 |

## Red Flags — 停下来自检

- 结论栏空着 → 审查必须有明确 PASS/FAIL
- 某条阻断意见没给具体改法 → 补上，否则执行者仍不知道怎么改
- 打算直接动手改用例 → 越界了
- 因为"用例整体还行"就判 PASS，但覆盖检查表里有需求点写着"无" → FAIL
